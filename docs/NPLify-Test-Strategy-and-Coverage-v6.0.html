1 · What this document is for

The pack already contains the yardsticks: the acceptance vectors of the Calculation Specification, the 61 worked transactions of the Ledger Posting Design, the state machines of the Lifecycle & Approvals document, the field groups of the Roles & Visibility Matrix, the constraints of the ERD's Appendix C and the exit criteria of the Cutover Approach. It did not say in one place which tests exist, what each proves, where it runs and what passing means. This document does. It is the testing framework Pete asked for: full scope, the purpose and expected result of every test, regression so the system stays robust as the project evolves, and a map from the Workflow Tree to the tests, so that well-tested and under-tested areas are visible.

3 · The acceptance gate per phase, and the regression rule

Every feature moves through the proposal's pipeline (mockup, build, QA, staging, UAT, production). Each phase closes with a demonstration against its gate; the gate is the set of tests below, all green. The regression rule: every release, in every phase and under the support bundle after go-live, runs the full vector, fixture, state and visibility suites, and a failing exact test blocks the release. A test is never removed because it fails; it is fixed or its expected result is changed with a recorded reason and NPL's agreement where the figure is NPL's.

4 · Identifiers and result classes

Every test has an identifier that never changes and is never reused (the same rule as the T, L, B, W, F and C identifiers of the pack; the Reading Companion's register lists them). The first letter says the family: V vectors and calculation, F fixtures and identities, S state machines, C concurrency and controls, D database, R roles and visibility, O operating procedures and UAT, G go-live acceptance. A purpose line says what the test proves. A result class says what passing means, so that a reviewer can tell a test with one right answer from a test whose result must only be reasonable:

Result classPassing meansExamples
exactThe result equals the expected value to the cent (eight decimals for BTC amounts, the unit where NPL's sheet rounds), or the expected state or refusal occursV-L1, F-T2, S-DEAL, D-CONS
toleranceThe result is within the rounding of the pair (a dropped fraction or a round-up with its owner)cash rounding cases; margin-of-the-day reconciliation
rangeThe result falls inside a configured band, because the right answer depends on data or judgementG-RECON checks with a tolerance; G-VULN severity; aging thresholds
invariantA property that must always be true holds after every step and every fixtureF-ID1…12, F-REPLAY, C-APPR, R-VIS, G-DUP

6 · Coverage sheet: the Workflow Tree against the tests

One row per sub-class of the Workflow Tree (27 sub-classes, 92 procedures). For each: where the procedures are written up, which client scenarios of the Scenario Catalogue use them, which ledger pattern books them, which tests exercise them and how many. A count of zero would be an open area; today none is zero, but the two lowest rows (6.2 payout methods, 7.5 ledger corrections) are where Phase 3 adds UAT cases first. The sheet is kept as a file next to the test suite (coverage.csv), with one row per procedure (the 92 leaves) filled in as the build phases land, and is shown at every phase review; the sub-class view here is its summary at the start of the build. Note: coverage.csv is a build-phase deliverable (Phase 1 onwards, maintained through Phase 3), not part of the P0 review cycle; its test column can only be filled once the test suite exists.
