1 · What this document is for

The pack already contains the yardsticks: the acceptance vectors of the Calculation Specification, the worked transactions of the Ledger Posting Design (61 numbered, T1 to T61; 67 fixtures once the variants T3a, T22a, T24a, T41a, T41b, T41c and T52a are counted, T41 existing only as its three variants — the Reading Companion's "67 worked transactions" is the same set; Appendix A is the one manifest), the state machines of the Lifecycle & Approvals document, the field groups of the Roles & Visibility Matrix, the constraints of the ERD's Appendix C and the exit criteria of the Cutover Approach. It did not say in one place which tests exist, what each proves, where it runs and what passing means. This document does. It is the testing framework Pete asked for: full scope, the purpose and expected result of every test, regression so the system stays robust as the project evolves, and a map from the Workflow Tree to the tests, so that well-tested and under-tested areas are visible.

3 · The acceptance gate per phase, and the regression rule

Every feature moves through the proposal's pipeline (mockup, build, QA, staging, UAT, production). Each phase closes with a demonstration against its gate; the gate is the set of tests below, all green. The regression rule: every release, in every phase and under the support bundle after go-live, runs the full vector, fixture, state and visibility suites, and a failing exact test blocks the release. A test is never removed because it fails; it is fixed or its expected result is changed with a recorded reason and NPL's agreement where the figure is NPL's.

4 · Identifiers and result classes

Every test has an identifier that never changes and is never reused (the same rule as the T, L, B, W, F and C identifiers of the pack; the Reading Companion's register lists them). The first letter says the family: V vectors and calculation, F fixtures and identities, S state machines, C concurrency and controls, D database, R roles and visibility, O operating procedures and UAT, G go-live acceptance', mk(', P the per-procedure tests of Section 6a (P-<procedure>-pos, -den, -rtr)'), '. A purpose line says what the test proves. A result class says what passing means, so that a reviewer can tell a test with one right answer from a test whose result must only be reasonable:

Result classPassing meansExamples
exactThe result equals the expected value to the cent (eight decimals for BTC amounts, the unit where NPL's sheet rounds), or the expected state or refusal occursV-L1, F-T2, S-DEAL, D-CONS
toleranceThe result is within the rounding of the pair (a dropped fraction or a round-up with its owner)cash rounding cases; margin-of-the-day reconciliation
rangeThe result falls inside a configured band, because the right answer depends on data or judgementG-RECON checks with a tolerance; G-VULN severity; aging thresholds
invariantA property that must always be true holds after every step and every fixtureF-ID1…12, F-REPLAY, C-APPR, R-VIS, G-DUP

6a · Per-procedure traceability: the money-moving, permission and exception procedures

A sub-class count above does not prove each of its procedures. For the procedures that move money, grant a right or handle an exception (classes 4 to 7 of the Workflow Tree, the two user-and-rights procedures of 1.4, and the two rights-bearing quote procedures 3.2.5 and 3.4.2) the test suite carries one explicit test per case and per procedure, named P-<procedure>-pos, -den and -rtr. The positive case (-pos) is the same for every row: the procedure completes with the initiator and approver the tree names, and the record, approval and posting it names exist exactly once. The gate is the milestone at which all of the procedure's cases must have run and passed; a procedure whose cases have not run does not pass its gate, whatever its sub-class count says. The denied and retry columns use codes: S — refused in the wrong state; R — refused for a role without the right (ROLE_RIGHT); P — refused when the approver is the person who initiated; M — refused until the Management approval exists (Management "always"; M(cond) where the tree makes it conditional); D — the same submission twice with the same idempotency key acts once and the second returns the first result (rule 1a); X — the partner's outcome is unknown: the line is held and no second instruction leaves (G-EXT).
