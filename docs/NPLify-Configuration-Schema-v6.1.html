1 · How configuration is organised

Four ideas carry the whole model. A client has projects. The client is the commercial relationship; each project is one arrangement with it, with its own settings, currency pairs, senders, receiver groups and partner configurations. Parties are partner-independent. Senders, receiver groups and receiving entities belong to the project, so the same Sender A → Receiver Y flow can run through Ali today and Jeton tomorrow. How a partner is used is a block. Fees and tiers, vehicles and their collection endpoints, the narrative and the rail that pay out, the destination approvals and the rebate rule all hang off one PARTNER_CONFIG, and a deal leg stamps the block's rows it was priced and routed on. The partner's clock is the partner's. Cutoff, time zone, holidays and overrides belong to the global PARTNER and apply wherever a pair says it relies on the banking channel.

1a · Creating a project, project states and effective-date rules

Creating a project from an archetype

A new project is not set up field by field. It is created from one of the six project archetypes of the Client Operating Procedures (Part C): the archetype pre-fills the project's policies, its currency pairs with their rate-source chains, the fee structure and tiers of each partner pair, the message templates, the thresholds and the partner configuration block. Finance then changes only what differs for the client (names, parties, accounts, the fee percentages agreed) and proposes the project; Management approves it as one change. An existing project of the same archetype may be used as the source instead of the archetype itself (cloning), with the same rules. The guided setup screens that do this are built in milestone M0 of Phase 1.

What a clone does not carry. Cloning copies structure, not agreements. The new project records its source (archetype code, or the project it was cloned from), every copied row carries that source until a user confirms or changes it, and the fields of the reconfirm list are left empty on the new project and must be set explicitly before it can be validated: on the project, client, name, client label, exposure ceiling, settlement policy and every threshold with an amount or a currency; on each partner pair, the fee structure's percentage and its sender and receiver parts, the tiers, the minimum and maximum markup and the rate basis; on each partner configuration block, the partner entities, collection endpoints, settlement sending entities and rails, destination approvals, rebate rule and markup shares; on the parties, the senders, receiver groups, receivers, accounts, bank account details and allow-lists. A partner's cutoff, time zone and holidays are never copied: they belong to the partner, not the project, and the new project reads them from the partner it names. The reviewer's case, an Evo-like project cloned for a partner on a different rail and cost, therefore fails validation on the rail, the partner fee and the fee percentage until each is set for the new agreement; the activation checks are rule 15 of Section 6, and the validation report names every failing row and field.

Project states: draft, validated, active

A project carries a state in addition to its status. draft: the project is being set up; rows may be added and changed freely under the normal proposal and approval rules; no deal can be priced on it. validated: every cross-entity rule of Section 6 passes for the project and for each of its partner configuration blocks; the validation report lists each rule with its result and the rows concerned, and is kept with the project. active: Management has activated the validated project; deals may be priced and partner configurations used. A project returns to draft when a change proposal is approved that makes a rule fail, and must be validated again before it is used. A partner configuration block added later follows the same path on its own: it cannot be used on a deal until it passes the rules of Section 6. The validation report screen is built in M0; the rules themselves already exist (Section 6) and are evaluated on save.

Effective-date rules

Configuration is versioned by effective date (Change control, below). The four rules below say what a new version does to deals that already exist. They are stated in the same words in section 2 of the Lifecycle & Approvals document.

RuleWhat happens
1. New versions apply to new pricing onlyAn approved configuration change takes effect for deals priced on or after its effective date. A deal priced before that date is not re-priced.
2. A priced deal keeps its versionsThe fee structure version, the tier, the rate basis, the rounding options, the partner configuration and the policy versions stamped at pricing stay with the deal to the end of its life, including through settlement, return and loss handling.
3. A re-quote uses the configuration of the new pricing timeAn expired or requoted leg is priced afresh on the versions in force when the new quote is made (a new deal group); the original leg keeps its stamp.
4. A collect-first deal uses the configuration in force when it is pricedA collect-first leg is priced at conversion, so it uses the versions effective at that time, not at the time the money arrived, unless a documented client agreement names a different rule for that project.

Worked scenarios (the fee rises from 2.0 % to 2.2 % effective 1 November; proposed 28 October, approved 29 October). A: quoted 30 October, collected 31 October, converted 2 November, pays 2.0 % (rule 2). B: quoted 2 November, pays 2.2 % (rule 1). C: quoted 30 October, expired, re-quoted 2 November, pays 2.2 % (rule 3). D: collected 31 October with no prior quote, priced at conversion on 2 November, pays 2.2 % (rule 4). These four scenarios are demonstrated in Phase 1 (M4) for fees, tiers, rounding options and partner settings, not only the headline percentage.

Change control. Configuration is versioned: thresholds, fee structures, tiers, templates, system settings and policies are new rows with an effective date, never edits. Finance proposes, Management approves (approver ≠ proposer, from the ROLE_RIGHT rows), and every change is audited. Deals keep the versions they were priced on. Three rows are not approvals but audited records: a partner cutoff override (Finance, with the partner's agreement), a wallet screening (Operations on a clear report; Management's decision on a second look) and a destination approval's status as reported by the partner.

6 · Cross-entity rules the system enforces on save

  1. Every project belongs to one client; a project's exposure_ceiling never exceeds its client's; both are compared through REPORTING_VALUE, so a platform pair must exist for every currency that rests at a partner.
  2. Every project has exactly one default receiver group, created by the system. A counterparty receiver is in exactly one group; sender_return and partner_transit receivers are group-less and never on a forward deal or an allow-list.
  3. Every sender has an allow-list naming groups of the same project and a sender_return receiver for refunds; a sender with no allow-list cannot be chosen on a deal.
  4. Every receiving entity has at least one account; accounts are unique per entity, currency and rail; a bank account names its BANK_ACCOUNT_DETAILS row, a wallet account a network and a checksum-valid address with rail = network. A single-use account or endpoint names the one deal it serves.
  5. A partner pair's currency pair is a project pair; partner_pricing agrees with the partner's disclosure_style; partner_fee_pct is present exactly for fee_on_market; needs_bank_lock requires the partner's bank_cutoff_time and cutoff_timezone.
  6. A fee structure's sender and receiver parts add up to its pct; min_markup ≤ max_markup; a fixed customer-facing fee names its pct; tiers have exactly one row at volume 0; a new version is a new row with a later effective_from.
  7. A partner configuration that will pay out needs at least one partner entity, one settlement sending entity (narrative) and one settlement rail. A bank endpoint cannot go active without a rail; a wallet endpoint's network is one the partner offers; an own-desk configuration needs an own wallet of role own_desk.
  8. A currency pair needs at least one rate source with a unique priority before it is usable; nearest_n and round_up_n need a rounding unit; cash rounding needs its unit. A platform pair has no project and ends in the reporting currency.
  9. A destination approval points at an account of a receiving entity in the same project; a quote-first deal for a group needs at least one approved destination with the chosen partner. A wallet account's approval carries its screening.
  10. A quote template prints sender-facing fields only; a screening decision of accept_alternate lands only on an elevated-band endpoint; on a report that is not clear under the Strict rulebook the decision is Management's second look, never a Finance override; a partner's hold, freeze or decline is recorded, never overridden; a cutoff override is a one-day or a weekday rule, never both; an extension names the partner's agreement.
  11. quote_freshness_min is shorter than quote_validity_min; all percentages are stored as decimals; Σ markup shares of one base ≤ 100 %; a rebate rule is pct_of_amount with a payout currency.
  12. applicable_for_reroute, is_own_desk, exposure ceilings, thresholds, fee structures and tiers, templates, system settings and platform pairs are Management-approved changes; users and roles need a second Management user.
  13. A project is validated only when rules 1 to 12, 14, 15 and 16 pass for it and for each of its partner configuration blocks; only a validated project can be activated, and only Management activates it. A partner configuration block added to an active project cannot be used on a deal until the rules pass for it.
  14. A bank account, a bank endpoint and a settlement rail name a BANK_ACCOUNT_DETAILS row of the same currency and rail and can be active only while that row is active; a row is saved only when the rail's template is satisfied (required fields present, format rules passed: IBAN check digits, BIC length, sort-code pattern) and its evidence is attached; a change to any detail is a new row that supersedes the old one, never an edit; a details row is approved by Finance or Management, never by the Operations user who entered it.
  15. A project created from an archetype or cloned from another project activates only when: every field of the reconfirm list of 1a is set on the new project itself, not inherited (a copied value counts only once a user has confirmed it on the row); every version the project references (fee structure, tiers, policies, thresholds, templates, platform pairs) is the version in force on the activation date, not one superseded since the source was set up; every partner configuration block's route is complete for the methods it will use (an active endpoint per collection method, a rail and a sending entity per bank payout, an approved destination for each group that will be paid, the partner's current partner_pricing, partner_fee_pct and cutoff); and ROLE_RIGHT rows exist for every controlled action with at least one approving role that is not the initiating role. The validation report lists each failure by entity, row and field with what fixes it; activation with any failure is refused.
  16. Email OTP. A project's Email OTP switch can be on only with the three Email OTP thresholds set. Each sender carries its own approver email and registered chat group (every sender has its own chat group); while the switch is on, a quote for a sender whose address and group are not present and approved cannot be sent, and the screen says why. The switch and the sender's four columns change only through set_email_otp_settings (Operations enters, Finance approves, never the same person); a new approver address is active only after its verification code comes back through that sender's chat group; while such a change is pending no approval email is sent for that sender; a change of address voids that sender's open codes only; switching the feature off is the same controlled change, and a group already pending completes or expires under the rules in force when it was sent; the partial destination printed in an email is derived from the approved endpoint bound to the quote issue, never typed (Lifecycle & Approvals 2e; Roles & Visibility rule 13).
