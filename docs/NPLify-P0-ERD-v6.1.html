Conventions

Convention: all monetary amounts are stored as exact decimals; every table carries created_at / created_by; audit, approvals and locking are modelled once (domain 4) and apply to all master data. Derived figures (client balance, group entitlement, offsets, custody) are views over postings and deals — never stored.

Seven diagrams across four domains, one schema: 78 tables and 12 views. In each diagram, boxes show the key fields only (full attributes in Appendix B) and are coloured by class — configuration and master data, rate reference, transactional event, ledger and control, derived view; a dashed box is a table drawn in another diagram and names it. Relationship lines run from the referenced row to the row that stores the foreign key; a dashed line is a reference or a polymorphic link resolved by a type column plus an id. The deal lifecycle has three diagrams: 3a is the deal and its collection, 3b the conversion and its exceptions, 3c the settlement. Appendix A reconciles the model with the FRS; Appendix B is the data dictionary.

Nothing among the 78 tables and 12 views of this edition, including the tables added in it (EMERGENCY_ACTION, PARTNER_STATEMENT_RECONCILIATION, OPENING_ENTRY), is deferred; the milestone estimates of the proposal stand.

Classification of the tables (fact and dimension)

Pete asked which tables are the facts and which the dimensions. In this model there are five classes; every table belongs to exactly one, and the diagrams (1a to 4) colour each box by its class. Configuration and master data are the dimensions: rows that describe how the business is set up, versioned by effective date and never edited. Rate reference is a time series of reference values. Transactional events are the facts: one row per thing that happened to a deal. Ledger and control tables are the facts of the books and the records that govern them. Derived views are never stored.

1 · Configuration domain

A Client is the commercial relationship NPL contracts with; a Project is one arrangement with it and owns its configuration. Partners are global counterparties; how a partner is used in this project is the partner configuration block — fees, vehicles, endpoints, destination approvals and rebate terms hang off it. Counterparty receivers are organised in receiver groups, the unit entitlement is tracked on, and each receiving entity holds one or more accounts with a currency and rail.

Notes

  • A Client is the commercial relationship NPL contracts with; a Project is one arrangement with it and owns its configuration. Counterparty receivers sit in receiver groups: every project has one default group and every counterparty receiver belongs to exactly one group. Entitlement is tracked per group, so payouts within a group are ordinary settlement and only payouts across groups are offsets; a project with a single group never has an offset.
  • A Receiver has a kind: counterparty for a client receiver; sender_return stands for a sender so refunds use the ordinary payout path and the partner's destination approval; partner_transit stands for a partner's collection endpoint so the hop of a two-leg route is an ordinary payout. sender_return and partner_transit receivers belong to no group (group_id is null). They never appear on forward deals or allow lists — both validate kind = counterparty — and a payout to them is attributed to the group of the leg that pays them, so no entitlement moves between groups on a refund or a hop. Groups exist for entitlement and offset accounting; refund exclusion is a receiver-kind rule, not a group.
  • A receiving entity holds one or more accounts, each with a currency and rail (EUR via SWIFT and EUR via SEPA are two accounts). An account is a bank account or a wallet (account_kind): a bank account carries bank_account_details_id and a bank rail; a wallet carries network and address explicitly, mirroring the partner-side COLLECTION_RECEIVING_ENDPOINT, so addresses can be checksum-validated, checked against the rail, and found when the same address is registered with two partners. Destination approvals and settlement lines point at the account. The bank details themselves are rows of BANK_ACCOUNT_DETAILS: a bank account carries bank_account_details_id, the current version of its details. A details row is never edited — a change is a new row that names the one it supersedes — so a settlement line released before the change still resolves to the details it was released against. The fields a rail needs (IBAN and BIC for SEPA; account or IBAN, BIC, bank address and intermediary for SWIFT; sort code and account number in the UK; bank code and account number on a local rail) come from BANK_DETAILS_TEMPLATE, which also carries the format rule each field is validated against on save. Only the evidence (bank letter, KYC, legal document) stays a file under the restricted prefix.
  • Fees are per partner × pair (FEE_STRUCTURE under PARTNER_PAIR), so choosing the partner is part of pricing. PARTNER.disclosure_style records whether the partner's markup is visible; partner_fee_pct is known only for fee_on_market partners.
  • A partner operates through one or more legal vehicles (PARTNER_ENTITY: PT-tour, PT Global Inc); the deal stamps the vehicle at quote so paperwork names the right company. Each vehicle owns the endpoints a sender can pay into (COLLECTION_RECEIVING_ENDPOINT): kind = bank with a currency and bank_account_details_id, or kind = wallet with network and address. The partner side therefore mirrors the client side — PARTNER_CONFIG → PARTNER_ENTITY → COLLECTION_RECEIVING_ENDPOINT as RECEIVER → RECEIVING_ENTITY → RECEIVING_ENTITY_ACCOUNT. An endpoint also carries a nullable rail: a bank endpoint must have it before it becomes active, and a wallet may leave it null but must match network when it is set; the endpoint's kind must match the leg's collection_method. Cash-in has no endpoint record; the leg carries the city and the collection the token. The collected cash amount is rounded by the pair's cash_rounding option — truncate, nearest or round up — to cash_rounding_unit (100 / 500 / 1,000 by currency), the same menu as payout rounding.
  • Destination approval is per partner: DESTINATION_APPROVAL is an account of the project's receiving entity as registered with this partner, carrying the partner's approval status and the payout details the partner holds. Those details follow the account's kind: bank_account_details_id (the details as registered with this partner) for a bank account, network and address for a wallet. SETTLEMENT_SENDING_ENTITY is the narrative on an outgoing transfer; SETTLEMENT_RAIL is the bank/EMI that executes it; neither holds money. COLLECTION_SENDING_ENTITY is provenance only and never a payout destination; its source account, when known, is a BANK_ACCOUNT_DETAILS row too.
  • OWN_WALLET has a role: reroute contingency (AQN-LT-Sub at Aquanow), own desk, or a collection bridge on a network a partner lacks, forwarded to the partner as a hop within the wallet's custody limit; PARTNER_CONFIG.applicable_for_reroute defines the alternate-partner set. PARTNER.supported_methods declares what a partner offers — cash and local deposits have no standing endpoint to read it from. WALLET_REGISTRY lists every known address with its owner and role. Under an own-desk partner configuration (is_own_desk, the NPL-GR game-reseller project) NPL itself is the converting party: its pairs are priced market plus NPL's markup and its collection endpoints are NPL's own wallets (COLLECTION_RECEIVING_ENDPOINT.own_wallet_id); the custody view reports every such balance.
  • Fees. A FEE_OVERRIDE may carry its own sender / receiver split instead of inheriting the structure's proportion. FEE_TIER rows under a structure price by the project's calendar-month volume; a leg that takes the month past a threshold is split across two tiers. customer_facing_fee_basis / customer_facing_fee_pct on the structure say what the customer's quote prints when it differs from the recorded parts; the printed "source rate" is derived at quote, never typed. CURRENCY_PAIR.amount_rounding is a menu — truncate, nearest or round up, to the unit or to rounding_unit — and a pair may have the same currency on both sides.
  • Who else earns on a deal. MARKUP_SHARE_PARTY / MARKUP_SHARE_RULE record a share NPL pays — or, with basis share_of_net_markup and party_kind client_party, the customer who provides a sub-account and shares NPL's markup (Raeen): the base is the leg's fee parts less its partner cost, rebates excluded, several parties may hold rules with different shares, and settlement_mode party_retains means the party holds the converted money and pays NPL the remainder monthly. PARTNER_REBATE_RULE records the rebate a partner pays NPL, with a basis (a percentage of the amount converted) and an optional scope by sender or fee structure; the rebate is NPL's alone and is reported as its own stream.
  • Project state and test twin. A project is priced against only when it is active (Configuration Schema 1a: draft, validated, active); PROJECT.is_test flags the dummy twin project used for scripted test deals, which the clean-target extract of the cutover leaves behind together with every row that belongs to it: the dependency closure and the checks on the production image are in Appendix C. THRESHOLD rows also carry the time limits per approval stage (approval_time_limit), the cutoff warnings (cutoff_warning_min), the lock idle time (lock_idle_minutes) and the three breach-rule values (rate_min_observations, rate_fallback_spread_abs, rate_abs_tolerance).
  • Cutoff, screening, single use. PARTNER.bank_cutoff_time (the partner's own clock, beside its rate expiry and holiday calendar), its per-day changes in PARTNER_CUTOFF_OVERRIDE (an agreed extension or an early close) and PARTNER_PAIR.needs_bank_lock drive same-day or next-day conversion and, on bank rails, same-day or next-day settlement. Cash legs carry their city (DEAL.cash_location) and cash rate versions theirs. WALLET_SCREENING records the screening of a sending or receiving wallet address, by Operations, and the endpoint's risk_band says which decisions may land on it. An endpoint or a receiving-entity account may be single_use, reserved for one deal (ad hoc local deposit accounts). HOLIDAY rows under the partner are the dates behind every "next business day"; MESSAGE_TEMPLATE is the versioned wording of outgoing messages and declares the fields it may print — a quote template prints sender-facing figures only.

2 · Rates domain

Diagram 2. RATE_SOURCE, CURRENCY_PAIR are defined in Diagram 1a; PARTNER_PAIR in 1b.

Notes

  • The rate comparison for the day is created lazily by the first deal that needs it, one per partner × pair × date, and reused by every deal that day. A partner may give a new rate during the day, so one date can hold several versions. Rolling averages are built from confirmed versions only.
  • A version is breached when spread > avg_2w × (1 + variance_threshold_rel); quoting and conversion on that partner × pair freeze until Finance approves with a reason, rejects, or asks for a better rate. Versions are never overwritten; every deal leg, conversion and balance conversion references its exact version.
  • Breach rules for thin or unusual history (Calculation Specification 2a): with fewer than rate_min_observations confirmed versions, or a zero or negative baseline, the fallback threshold rate_fallback_spread_abs applies; a spread beyond rate_abs_tolerance from the average in either direction is flagged for Finance. The three values are THRESHOLD rows of the project.
  • Cross-source slippage is a query over MARKET_RATE across sources for the same pair and window.
  • A version stores the rate as the partner quoted it (quoted_rate, quoted_direction); rate is normalised to the pair's direction and derived — 1 ÷ quoted when the directions differ — so Ali's 1.1738 becomes 0.851934 without a hand inversion, and a direction slip is caught by the breach check. Cash pairs are priced per location: INR cash in Delhi and in Mumbai are two versions on the same day.

  • Email OTP (CR-01). On a project with the feature on, a quote issue is an approval email with a one-time code, and the customer's acceptance is that code entered by Operations from the registered chat group: CUSTOMER_APPROVAL (one row per code; hash only; write-once decision; the email snapshot and the chat screenshot as evidence) and CUSTOMER_APPROVAL_EVENT (sends, deliveries, replies, attempts). The group's states are unchanged: Sent is pending customer approval, Accepted is customer approved. The settings sit on PROJECT (the switch), SENDER (one approver address and one registered chat group per sender, because each sender has its own chat group) and THRESHOLD (code window, step-up amount, tripwire window). Both tables are in Appendix B.3 and drawn in Diagram 3a beside the quote package.
  • Every deal belongs to a deal group. DEAL_GROUP is the client-facing instruction: the pair as the sender sees it, the sender rate, fee, reference and entry mode. A plain single-partner deal is a group of one leg; a route that needs two partners (INR → USDT at Ali, USDT → EUR at Jeton) has two forward legs; a rejected payout is unwound with a return leg.
  • Legs. leg_type forward or return; funding_source collection, prior_leg (leg 2 of a route, no collection) or returned_settlement (a return leg). Priced once and partner fixed at quote hold per leg. Attribution is to the receiver group: set at quote on the first forward leg, inherited by leg n of a route from leg n−1 and by a return leg from its parent leg. The receiver is optional until settlement.
  • Two entry modes as before: collect-first legs are born in state Collected with priced_at = conversion time; quote-first legs carry sent / valid / grace timestamps and a late decision. An estimate-first mode gives an indicative figure and prices at conversion.
  • Conversion has exactly one owner: a deal leg or a BALANCE_CONVERSION. The receiver-side fee is taken at conversion. Amounts are rounded at conversion by the pair's option; a dropped fraction (rounding_residual, signed) stays client money in the balance and pays out when it reaches a unit, an amount added by rounding up is NPL's cost. NPL's margin is captured at conversion and is never again at risk from a return or a forward.
  • Balance conversion is NPL converting a client's held balance (5K SGD → USDT to fund a 15K USDT payout): Finance-initiated, Management-approved, no sender, receiver or collection, same rate machinery, markup by FEE_DECISION. It names the receiver group it serves; ENTITLEMENT_REATTRIBUTION moves that group's entitlement to the new currency, and any excess over the group's entitlement is booked as an approved offset.
  • Reroute is the only way partner or partner entity change after quote. Forwarding is forward_full or forward_and_recover_dues: NPL nets what the alternate partner owes it (EARNINGS_RECEIVABLE) against the funds forwarded, within the outstanding receivable, with the partner's agreement recorded. Post-collection outcome is via the own wallet or a refund to the sender. A reroute after conversion (phase post_conversion, NPL decision of 20 October 2026) starts from a leg in Converted: the converting partner converts the balance back to the collection currency (return_conversion_id, a balance conversion owned by the reroute, no markup), pays it to NPL's own wallet, and NPL forwards it to the alternate partner, which converts at its own rate of the day (second_conversion_id); the leg's client net is unchanged, the rate_difference is NPL's gain or cost (VAR_CONVERSION, Ledger Posting Design Pattern O), and Management's ratification (ratified_by) is needed in addition to Finance's because NPL's wallet holds client money in the meantime. Own-wallet custody cases therefore become four.
  • One settlement model: SETTLEMENT drains one partner's holding into one or many SETTLEMENT_LINEs, rounded as the pair says. Under settlement_policy to_zero the balance after release is less than one unit; under hold_allowed the balance may rest at the partner within the project's exposure cap.
  • A settlement line records when it was released (released_at), by when the rail should confirm it (expected_confirmation_by) and when it ended (confirmed_at), so the named state "sent, not yet confirmed" can be shown and aged (Lifecycle & Approvals §7; Ledger Posting Design rule 13a). The promise is discharged on release; a return or a short delivery re-raises it.
  • A line paying a counterparty receiver whose group differs from the paying leg's attributed group is an offset, created by the same action, with Management approval and tighter aging. A line paying a sender_return or partner_transit receiver is never an offset: those receivers have no group, and the line debits the group of the leg it names in deal_id.
  • Rejected payout. When the receiving or intermediary bank rejects a transfer, SETTLEMENT_RETURN records the returned amount, bank fee and reason; the line's outcome becomes returned, a reversing ledger transaction puts the money back into the client's balance and the paying leg's group entitlement, and BANK_FEE_EVENT books the bounce fee. The money then stays in balance for later payouts, or funds a return leg — attributed to the same group — that converts back and pays the sender's return receiver.
  • Fee decisions. FEE_DECISION is a one-off, approved decision on a single subject: markup applied or waived on a return leg or balance conversion, a network-fee override on a refund, a bank-fee treatment override on one settlement. Standing rules stay in FEE_STRUCTURE and FEE_OVERRIDE.
  • CONFIRMATION is full or short; a short confirmation opens a SHORTFALL topped up by a later settlement or an explicit separate payout — cash found short at hand-over included. Rounding differences no longer land here. MARKUP_SHARE_ACCRUAL and PARTNER_REBATE_ACCRUAL accrue per deal under their rules; a party_retains markup-share accrual is a receivable from the party, reconciled monthly like a rebate; rebates are reconciled monthly against the partner's statement, which covers NPLify deals only.
  • Pricing stamps. A leg stamps the override and the base tier that priced it; a leg that crosses a tier threshold holds two DEAL_FEE_TIER portions and a blended fee. The deal group stamps the customer-facing fee and rate the quote printed. On a pair that needs a bank lock the leg records rate_locked_at and conversion_due_date: locked before the partner's cutoff it converts the same day, otherwise the next business day at that day's version; the sender's figures are write-once, NPL absorbs the difference as a cutoff-timing variance, and a conversion whose next-day rate breaches the margin is deferred with a reason. The client balance view shows the locked leg's converted value as pending from the lock; a void removes it. QUOTE_PACKAGE is the record of what was sent for a deal group — template version, channel, printed figures, sent_at, hash — one row per issue; a quote-first leg is Sent only when a package has sent_at, re-issues are new rows, a new price is a new deal group.
  • Invoices. INVOICE is an obligation in its own currency — a vendor's EUR invoice a reseller customer pays in THB or USDT, in parts, over days. A deal group names the invoice it pays (advance, then balance); each payout line records how much of the obligation it discharged and the market snapshot used; INVOICE_BALANCE is the open remainder.
  • Cash and crypto parts. A cash part carries the token (the local-currency bill whose serial identifies the agent), the agent's contact and the partner's count; the leg carries the city, which also selects the rate version. A crypto part carries the sender's declared address and the screening that admitted it, unless the project skips up-front screening.
  • Loss events. LOSS_EVENT records money lost after it was verified or released — a frozen local account, cash short that cannot be recovered, a wrong-chain transfer — on either side, by any method, for a partial or full amount, with the loss split across sender, NPL, partner and client. The whole loss is booked to NPL and the client made whole in one transaction (source LossEvent; MAKEGOOD / LOSS_PAYABLE when it cannot be funded at once); Management approves the split and each share is a separate LOSS_RECOVERY posting; the collection part stays verified and is reversed only when the deal is unwound.

4 · Ledger & controls domain

Diagram 4. PROJECT is defined in Diagram 1a; INVOICE in 3a.

Notes

  • Client due balances are held as one account per project × partner × currency (CL.<PARTNER>.<CCY>.DUE); group entitlement is a view, not an account. holder_type never includes a settlement rail or narrative entity.
  • Ownership moves between client and company only at named events — margin recognition at conversion, the two sides of an earnings offset, the forex true-ups of invoice lines, fees NPL absorbs or covers, top-ups, make-wholes, make-goods and the client's loss share — and every transaction balances per owner as well as per currency. NPL never advances money to a receiver, and withholding on a reroute is not a separate event because the margin is always captured by whichever partner converts.
  • Recover dues on a reroute posts own-wallet cash against the earnings receivable at the partner: company money on both sides, no income.
  • Transaction sources: Collection, Conversion, BalanceConversion, Settlement, SettlementReturn, Confirmation, BankFeeEvent, Reroute, MarkupShare, Rebate, LossEvent, LossRecovery, Invoice, EarningsOffset, Adjustment, Opening. Account purposes include PAYABLE, SHARE_PAYABLE, SHARE_RECEIVABLE, REBATE_RECEIVABLE, LOSS_RECEIVABLE, MAKEGOOD / LOSS_PAYABLE, EARN_GROSS, EARN_REBATE, the four VAR_ accounts, FX_RESULT, the reseller purposes (RESELL_REVENUE, RESELL_COST, VENDOR_PAYABLE, RESALE_RECEIVABLE, REMIT_CLAIM), EXP_ROUNDING and EXP_LOSS; ADVANCE and INTRANSIT do not exist. Cost components include share, rebate, rounding, fx_timing, cutoff_timing, loss and resale.
  • Three streams NPL never mixes. Earnings on deals post to EARN_GROSS at conversion; a partner's rebate posts to EARN_REBATE and is never in the base a client party shares; NPL's remainder from a party that holds the converted funds sits in SHARE_RECEIVABLE until the party pays it. The cost of rounding up is EXP_ROUNDING. A loss is booked to EXP_LOSS in full first and the client made whole; the partner's and the sender's agreed shares are LOSS_RECEIVABLE owed to NPL, the client's share is a partial reversal of the make-good, and what remains in EXP_LOSS is NPL's own share. Own-desk deals use the ordinary partner-coded accounts with the own-desk configuration as holder and EXP_PARTNER zero by construction.
  • One system-settings area: SYSTEM_SETTING holds NPL-wide, Management-approved keys — the reporting currency, its staleness limit, the operating time zone; ROLE holds the user roles and ROLE_RIGHT what each may initiate and approve per controlled action, with the role added on escalation; platform-scope CURRENCY_PAIRs carry the conversion rates through the ordinary rate-source chain. REPORTING_VALUE converts any per-currency figure into the reporting currency at the latest market rate of its platform pair, as a display-only estimate that carries the rate it used. APPROVAL, AUDIT_LOG and RECORD_LOCK are modelled once and apply to all master data. Approver ≠ initiator on every approval; Operations never sees derived economics. Approval actions include price_quote, extend_quote_validity, refund_to_third_party, cross_group_payout, balance_conversion, recover_dues, cover_bank_fee, raise_fee_cap, enable_own_desk, approve_loss_split, screening_second_look, earnings_offset, bank_details_approve and the four Email OTP actions (ROLE_RIGHT rows). cross_group_payout never fires on a line paying a sender_return or partner_transit receiver. Wallet screening itself is an Operations action, not an approval.
  • Three tables of this edition. OPENING_ENTRY is one row per opening balance entered on the opening date (Cutover Approach, Section 4; Ledger Posting Design, Pattern R), posted once, one transaction per row (source Opening): company-side balances against CO.NONE.<CCY>.OPENING_BALANCE, client-side balances between the client's jar and the project's promise, and OPENING_BALANCE is never posted to again. PARTNER_STATEMENT_RECONCILIATION is one row per partner configuration, currency and statement date (Pattern Q): a row for every business day of the parallel run and for every month end afterwards, a difference cleared only by a true-up transaction, never by an edit, and a row in state difference_open on the exception list. EMERGENCY_ACTION is the record behind the controlled action emergency_suspend (Lifecycle & Approvals, section 5): applied by Finance, in effect at once, lifted unless Management ratifies it within one business day; ratified_by is never applied_by. LEDGER_TRANSACTION.corrects_period names the month a correction belongs to when it is posted in a later month (rule 11a).
  • Controls on the person and the record version. The approver is never the initiator on the person: USER.person_ref names the natural person behind every account, and APPROVAL.approved_by is refused when its person_ref equals requested_by's, so a user holding two accounts cannot approve their own request (Roles & Visibility rule 5a). An approval is valid only for the record version the approver saw, so two approvers at once leave exactly one winner and a changed record is re-approved (Lifecycle & Approvals 6a). At most one open lock per record: a RECORD_LOCK is released on save or cancel, expires after the project's lock idle time, or is cleared by Management, and every release is written to AUDIT_LOG. Rules at database level are listed in Appendix C: postings balance per currency and per owner; ledger and audit tables accept inserts only; every PAYABLE line carries its receiver group; the seven type-plus-id references are checked by one generic trigger; the approver's person_ref differs from the initiator's; versioned configuration is write-once.

Type-plus-id references: option b, one generic trigger

NPL chose option b on 19 October: the type-plus-id references stay as they are and one generic database trigger checks, on insert and update, that the id exists in the table the type column names, and refuses the row otherwise. The trigger is applied to all seven such references: LEDGER_TRANSACTION (source_type, source_id), LEDGER_ACCOUNT (holder_type, holder_id), APPROVAL (subject_type, subject_id), AUDIT_LOG (record_type, record_id), RECORD_LOCK (record_type, record_id), FEE_DECISION (subject_type, subject_id) and EMERGENCY_ACTION (subject_type, subject_id); DEAL.funding_ref_id is checked against the table funding_source names in the same way. The trade-off accepted: the database cannot cascade or report these as foreign keys, so a referenced row can never be deleted (none of these tables deletes), and a type value is added by a row in the TYPE_REGISTRY table the trigger reads (type value → table name → the column that carries the project, where one exists), never by editing the trigger; a value the registry does not know is refused. The acceptance test inserts a row whose id does not exist for each of the seven references and expects a refusal. The four discriminator-plus-column references (WALLET_SCREENING.subject_kind, LOSS_EVENT.side, RECEIVER.kind, CONVERSION's one owner) are ordinary foreign keys with a CHECK that exactly the right column is set.

Critical sources: three checks, not one

For the ledger (LEDGER_TRANSACTION.source_type, source_id) existence is not enough, because an id that happens to exist in another table would pass an existence check under the wrong type. Three checks apply to every ledger source, and the first two to the other six references: (1) the type value is in TYPE_REGISTRY; (2) the id exists in the table the registry maps the type to; (3) for a ledger source, the source row's project (read through the registry's project column: the deal's project for a Collection, Conversion or Settlement line, the balance conversion's, the reroute's, the opening entry's) equals the transaction's project, so a Settlement id of another project is refused as firmly as a missing one. The negative tests D-POLY8 to D-POLY10 insert, for each reference, an unknown type, an id that exists only in another table and a ledger source of another project, and expect a refusal from the database and from the API; a restore into a scratch instance re-runs the same three checks as a scan and reports every broken link (G-RESTORE).

Immutable evidence references

Six columns name a file: COLLECTION.evidence_ref, SETTLEMENT_LINE.evidence_ref, WALLET_SCREENING.evidence_ref, OPENING_ENTRY.evidence_ref, BANK_ACCOUNT_DETAILS.evidence_ref and PARTNER_STATEMENT_RECONCILIATION.statement_ref. Each is write-once (a trigger refuses an update once the value is set; a corrected document is a new row that names the old one, as everywhere in the model) and content-addressed: the object key carries the file's SHA-256, the bucket keeps every version with an object lock, and the application rejects an upload whose hash does not match the key it is stored under. A reference therefore resolves to exactly the bytes that were attached, or to nothing; it can never resolve to a changed file. The restore audit re-hashes every object the extracted rows name and reports a missing or altered one (D-POLY11, G-RESTORE).

The checks on the image, run by the extract before its one commit and again after every restore from backup (Cutover 8a), are the automated scan the reviewer asks for: (1) every FOREIGN KEY resolves — the load runs with constraints deferred and commits once, so a dangling key fails the whole load; (2) every type-plus-id reference resolves through the registry, with the three checks above; (3) the closure inverted from the test projects reaches zero rows of the image; (4) the count per table equals staging's count of real-project rows, computed by the same closure on staging; (5) the ledger identities of the Ledger Posting Design (Section 20) hold and every balance per project, partner and currency equals staging's; (6) every evidence object is present and its SHA-256 equals its key; (7) the extract writes one AUDIT_LOG row in production (record_type Extract) naming the staging snapshot, the counts per table, the test accounts left out and the result of each check. Any check that fails leaves production empty (Cutover, rollback).

Audit retention. The production AUDIT_LOG and ledger accept inserts only and are never pruned. The audit rows of the test projects are not in production; they are in the staging snapshot, which is kept read-only as the record of the parallel run, test projects included, for the retention period NPL sets (a SYSTEM_SETTING; proposed: the same period as the ledger's). Nothing of the run is therefore lost: production holds the real projects' audit from their first staging entry, and the snapshot holds the rest.
