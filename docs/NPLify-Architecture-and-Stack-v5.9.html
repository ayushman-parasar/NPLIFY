Status: NPL's architecture and stack page of October 2026 — one app with one database in NPL's own AWS account, for a small team handling about ten deals a weekday — expanded against ERD & Data Model Draft v5.9, the Ledger Posting Design v5.9 and the Roles & Visibility Matrix v5.9. Nothing on NPL's page is changed; this note says what each piece has to do for the model to hold: which tables and views live where, which background jobs the clocks and checks of the model require, how the insert-only ledger and the visibility rule are enforced in the database and not only in the screens, and the staging instance the cutover plan adds to the two environments. Items NPL still has to decide are collected in Section 9.
Audience: NPL Management and the New XP engineering team.

1 · In one paragraph

NPLify is an internal tool. It runs as one application — screens, API and background jobs in a single Next.js / TypeScript service — against one PostgreSQL database whose ledger and audit tables accept inserts only, with one S3 bucket for slips, screenshots and photos, all inside NPL's own AWS account in Hong Kong. Staff sign in with NPLify's own login: email, password and a code from an authenticator app; users, roles and rights are rows in NPLify. Four outside services are used and none is trusted with the books: Kraken and CoinMarketCap for market rates, Tronscan and Etherscan to check transaction hashes, and one Google Sheet per client as that client's status journal. Daily backups are kept thirty days with restore to any minute. The running cost is about USD 50–80 a month. At ten deals a weekday the whole model is a few thousand rows a month; nothing here is sized for more than that, and nothing needs to be.

3 · The insert-only ledger, enforced by the database

NPL's page says the database refuses updates and deletes on ledger and audit tables. In the model that is invariant 2 — ledger tables are append-only; corrections are reversing transactions — and it is enforced in three layers so that no screen, no job and no mistake can get around it:

  1. Privileges. The application's database role has INSERT and SELECT on LEDGER_TRANSACTION, LEDGER_POSTING, LEDGER_ACCOUNT and AUDIT_LOG and no UPDATE or DELETE. Nobody uses the owner role day to day; schema changes are migrations run by deployment under a separate role.
  2. Triggers. A BEFORE UPDATE OR DELETE trigger on the same tables raises an error whatever the role, so even an operator connected as the owner cannot change a posting by hand. LEDGER_ACCOUNT allows one exception: a row's status may be changed to closed; its code, owner, holder, currency and purpose may not.
  3. Balance at commit. A deferred constraint trigger on LEDGER_POSTING checks, when a transaction commits, that its postings sum to zero per currency and, separately, per ownership tag (invariant 1), that every CL.PROJECT.<CCY>.PAYABLE line carries a receiver_group_id (invariant 7), and that the transaction names a source record of the stated source_type. An unbalanced transaction never reaches the books.

Everything else in the model is a normal row with a lifecycle (a deal, a settlement, a conversion, an approval) or a versioned configuration row (a fee structure, a threshold, a template, a system setting: new rows with an effective date, never edits). For those, AUDIT_LOG holds every field change with old and new value and the acting user, written by the API in the same database transaction as the change, and RECORD_LOCK prevents two people editing one record at once. Reversal is the only correction: LEDGER_TRANSACTION.reversal_of_id names the transaction reversed, and the Adjustment source is a Finance-initiated, Management-approved action (Lifecycle & Approvals §5).

Views, not stored balances. The 12 views — PROJECT_BALANCE, GROUP_ENTITLEMENT, OFFSET, CUSTODY, INVOICE_BALANCE, PROJECT_MONTH_VOLUME, CLIENT_POSITION, WALLET_REGISTRY, REPORTING_VALUE, RESELLER_MARGIN, REMITTANCE_MARGIN, NPL_PROFIT — are SQL views (materialised only if a screen is ever slow, refreshed on commit). PROJECT_BALANCE is the sum of CL.<PARTNER>.<CCY>.DUE postings; GROUP_ENTITLEMENT the sum of PAYABLE postings by receiver_group_id; CLIENT_POSITION a roll-up over the client's projects; REPORTING_VALUE a conversion at request time. Operations' one figure, the amount available to pay out at a partner, is PROJECT_BALANCE read through the field filter.

4 · Background jobs the model needs

NPL's page names quote clocks, rate fetch and alerts. The model's clocks and checks need the nine jobs below; all run inside the single app process on a schedule table, each run recorded with its outcome so the exception list can show a job that failed. None of them moves money: a job may stamp a clock, expire a quote, attach evidence or raise an alert, but every posting is made by a controlled action of a person (or by the engine as part of one).

5 · Screens, API and the visibility rule

There is one application with three views of it, by role. The Operations screens are the working day: inquiries and quotes, the quote package, wallet screening, collections to verify, conversions to instruct, settlements to prepare, destination approvals, loss events to record, the client journal; the Finance screens add the approvals queue, the partner rate versions and the day's comparison, variance and other exceptions, reconciliation, earnings resting at partners and offsets, invoices and the reseller books, statements, the Finance Log; the Management screens add the escalations queue, configuration proposals to approve, system settings, users and roles, and the reports in the reporting currency. Every screen is served by the same API, and the API applies the rule of the Roles & Visibility Matrix at the point where a response is built: for a role whose ROLE.sees_economics is false the fields of the groups Reference rate and comparison, Margin, pool, cost breakdown and Ledger and balances are removed before the data leaves the server, on every read, list, export, document and notification. The browser never receives what the role may not see, so there is nothing to hide in the page.

Three API conventions carry the state machines: every state change is a named action (POST /deals/{id}/actions/instruct-conversion), never a field edit; an action that needs approval creates the APPROVAL row and returns the state the record is now in; the approver's call is a second action by a different user, checked against ROLE_RIGHT (invariant 9). Idempotency keys on every money-moving action, so a retried request cannot post twice.

S3 objects are keyed by record type and id (collections/{id}/evidence/{n}), the key is the reference, and the bucket's versioning means an overwritten slip is still there. The cutover plan NPL described on 11 October (a staging instance for the parallel run, then copy its database to production) keeps the single reset and adds the temporary staging instance; the two documents are consistent on that basis.

  • Backups. Daily automated snapshots of the database kept 30 days, with point-in-time restore to any minute in that window (RDS automated backups); S3 versioning for files. A weekly restore test (Section 4, last job). A restore is a Management decision recorded in the audit log, because the ledger after a restore is the ledger as of that minute and the sheets fill the gap.
  • Monitoring. The app's own exception list is the first monitor; underneath it, the account's basic alarms: service unhealthy, database storage or connections, a job run that failed twice, a rate feed stale for more than ten minutes, a journal row unconfirmed for more than an hour. Alerts go to Finance and the engineering contact.
  • Deployment. One container image per release, built from the repository, migrations applied on start under the migration role, a release note that names the ERD edition the schema matches (the version of erd.v5.json, 5.9 today).

9 · Decisions for NPL and assumptions made here

  1. Container service. App Runner (simplest) or ECS on Fargate (more control); both fit the cost line. Assumed: App Runner.
  2. Wallet screening provider (D31): which tool, and whether the app calls it or Operations pastes the result. Assumed: pasted result with evidence until a provider is chosen.
  3. The restricted store for bank details, KYC and legal documents: the same bucket under a restricted prefix (assumed), or a separate secrets store.
  4. Manual rates are modelled as a RATE_SOURCE of code MANUAL so a manual rate is an ordinary MARKET_RATE row with its approval; the ERD's RATE_SOURCE.code list (KRAKEN / CMC / OANDA / XE) would gain MANUAL. Proposed as an ERD addition with the cutover's OPENING purpose.
  5. Client journal content: which state changes and which fields each client sees; assumed the sender-facing set of MESSAGE_TEMPLATE quote plus state and timestamps, per client.
  6. USER.email is described in the ERD as a Google Workspace address; with NPLify's own login it is only the sign-in name. No change to the model; a note for the next ERD edition.
  7. Availability. A single task and a single-AZ database are assumed; a short outage falls back to the sheets. Multi-AZ roughly doubles the database line and is not proposed at this scale.
