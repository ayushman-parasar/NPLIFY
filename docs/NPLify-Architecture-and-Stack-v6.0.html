1 · In one paragraph

NPLify is an internal tool. It runs as one application — screens, API and background jobs in a single Next.js / TypeScript service — against one PostgreSQL database whose ledger and audit tables accept inserts only, with one S3 bucket for slips, screenshots and photos, all inside NPL's own AWS account in Hong Kong. Staff sign in with NPLify's own login: email, password and a code from an authenticator app; users, roles and rights are rows in NPLify. Four outside services are used and none is trusted with the books: Kraken and CoinMarketCap for market rates, Tronscan and Etherscan to check transaction hashes, and one Google Sheet per client as that client's status journal. Daily backups are kept thirty days with restore to any minute. Running cost with the resilience decided on 20 October: about USD 165 to 245 a month (Section 6). At ten deals a weekday the whole model is a few thousand rows a month; nothing here is sized for more than that, and nothing needs to be.

3 · The insert-only ledger, enforced by the database

NPL's page says the database refuses updates and deletes on ledger and audit tables. In the model, ledger tables are append-only and corrections are reversing transactions, and that is enforced in three layers so that no screen, no job and no mistake can get around it:

  1. Privileges. The application's database role has INSERT and SELECT on LEDGER_TRANSACTION, LEDGER_POSTING, LEDGER_ACCOUNT and AUDIT_LOG and no UPDATE or DELETE. Nobody uses the owner role day to day; schema changes are migrations run by deployment under a separate role.
  2. Triggers. A BEFORE UPDATE OR DELETE trigger on the same tables raises an error whatever the role, so even an operator connected as the owner cannot change a posting by hand. LEDGER_ACCOUNT allows one exception: a row's status may be changed to closed; its code, owner, holder, currency and purpose may not.
  3. Balance at commit. A deferred constraint trigger on LEDGER_POSTING checks, when a transaction commits, that its postings sum to zero per currency and, separately, per ownership tag, that every CL.PROJECT.<CCY>.PAYABLE line carries a receiver_group_id, and that the transaction names a source record of the stated source_type. An unbalanced transaction never reaches the books.

Everything else in the model is a normal row with a lifecycle (a deal, a settlement, a conversion, an approval) or a versioned configuration row (a fee structure, a threshold, a template, a system setting: new rows with an effective date, never edits). For those, AUDIT_LOG holds every field change with old and new value and the acting user, written by the API in the same database transaction as the change, and RECORD_LOCK prevents two people editing one record at once. Reversal is the only correction: LEDGER_TRANSACTION.reversal_of_id names the transaction reversed, and the Adjustment source is a Finance-initiated, Management-approved action (Lifecycle & Approvals §5).

How the jobs stay reliable

Four rules apply to every job above, and to the tenth job added on 20 October, the fallback workbook export (every 15 minutes: open deals and their states, partner balances, the day's confirmed rates, cutoffs and pending approvals, written to a Google Sheet that NPL restricts to the people who need it).

RuleWhat it means
One run at a time per jobEach job takes a lock row before it runs and releases it at the end (Lifecycle & Approvals 6a); a run that finds the lock held exits at once and is recorded as skipped. Two tasks in two zones therefore never run the same job together.
Catch-up after a restartA job resumes from the last recorded run, not from now: rate capture fills the gap it can, quote clocks expire what passed, the aging job rebuilds the list. A deployment or a zone failure delays a job; it never loses one.
Bounded retriesA run that fails is retried three times with a growing wait, then left for the next schedule; the failure is recorded with its reason and raises the account alarm after the second failure (Section 6, Monitoring). Nothing is retried forever, and nothing that failed is silently skipped.
A job-health line on the exception listThe exception list every role sees shows, for each job, its last successful run, its last failure and whether it is overdue, so a stale rate feed or a stopped journal writer is visible to Operations before a deal is affected.

None of this moves money: a job still never posts (Ledger Posting Design, Pattern P). Built in Phase 1 with the jobs; the concurrency test of the go-live acceptance starts a job twice and expects one run (Cutover Approach, exit criterion 10).

5 · Screens, API and the visibility rule

There is one application with three views of it, by role. The Operations screens are the working day: inquiries and quotes, the quote package, wallet screening, collections to verify, conversions to instruct, settlements to prepare, destination approvals, loss events to record, the client journal; the Finance screens add the approvals queue, the partner rate versions and the day's comparison, variance and other exceptions, reconciliation, earnings resting at partners and offsets, invoices and the reseller books, statements, the Finance Log; the Management screens add the escalations queue, configuration proposals to approve, system settings, users and roles, and the reports in the reporting currency. Every screen is served by the same API, and the API applies the rule of the Roles & Visibility Matrix at the point where a response is built: for a role whose ROLE.sees_economics is false the fields of the groups Reference rate and comparison, Margin, pool, cost breakdown and Ledger and balances are removed before the data leaves the server, on every read, list, export, document and notification. The browser never receives what the role may not see, so there is nothing to hide in the page.

Three API conventions carry the state machines: every state change is a named action (POST /deals/{id}/actions/instruct-conversion), never a field edit; an action that needs approval creates the APPROVAL row and returns the state the record is now in; the approver's call is a second action by a different user, checked against ROLE_RIGHT. Idempotency keys on every money-moving action, so a retried request cannot post twice.

  • Backups. Daily automated snapshots of the database kept 30 days, with point-in-time restore to any minute in that window (RDS automated backups); S3 versioning for files. A weekly restore test (Section 4, last job). A restore is a Management decision recorded in the audit log, because the ledger after a restore is the ledger as of that minute and the sheets fill the gap.
  • Recovery objectives and resilience (NPL decision, 20 October 2026). Recovery time: one hour in operating hours. Recovery point: 15 minutes, and near zero for a hardware failure, the evidence bucket included. To meet them, three things are part of the design rather than options: a Multi-AZ database (a hot standby in a second availability zone with automatic failover, roughly doubling the database line of the running cost), two application tasks in two zones, and a daily cross-region copy of the backup. Engineering restores, Finance validates the financial data after any recovery, Management authorises a production restore and the resumption of processing; the steps are the recovery runbook of the Cutover Approach (8a). The fallback workbook, an export refreshed every 15 minutes to a Google Sheet with open deals, balances, rates, cutoffs and pending approvals, is the tenth job of Section 4 and is built in Phase 2 (M7).
  • Monitoring. The app's own exception list is the first monitor; underneath it, the account's basic alarms: service unhealthy, database storage or connections, a job run that failed twice, a rate feed stale for more than ten minutes, a journal row unconfirmed for more than an hour. Alerts go to Finance and the engineering contact.
  • Deployment. One container image per release, built from the repository, migrations applied on start under the migration role, a release note that names the ERD edition the schema matches (the version of erd.v5.json, 6.0 today).

Schema change policy. Every change to the database is a numbered, forward-only migration kept in the repository with the code that needs it; there is no manual change to a live schema. Before release, each migration is run against last week's restored snapshot (the weekly restore test of Section 4) and the ledger checks are run on the result, so a migration that would break a balance or an invariant is caught on a copy. Migrations on LEDGER_TRANSACTION, LEDGER_POSTING, LEDGER_ACCOUNT and AUDIT_LOG are additive only: a column may be added, never removed or retyped, and no migration updates or deletes a posting. The release note names the migration numbers it carries and the ERD edition the schema matches, and the first start of the new image applies them under the migration role (Section 6, Deployment).

7 · Decisions for NPL and assumptions made here

  1. Container service. App Runner (simplest) or ECS on Fargate (more control); both fit the cost line. Assumed: App Runner.
  2. Wallet screening provider: which tool, and whether the app calls it or Operations pastes the result. Assumed: pasted result with evidence until a provider is chosen.
  3. The restricted store for KYC, legal documents and bank letters: the same bucket under a restricted prefix (assumed), or a separate secrets store. Bank account details are no longer files: they are rows of BANK_ACCOUNT_DETAILS, read-logged (decision of 26 October 2026).
  4. Client journal content: which state changes and which fields each client sees; assumed the sender-facing set of MESSAGE_TEMPLATE quote plus state and timestamps, per client.
  5. Availability, decided on 20 October 2026 with the one-hour recovery target: a Multi-AZ database (a hot standby in a second availability zone with automatic failover) and two application tasks in two zones, so that one zone's failure neither loses the database nor stops the application. The cost of both is in the table of Section 6. The residual risk accepted is a whole-region outage, covered by the daily cross-region backup copy and the recovery runbook (Cutover Approach 8a), with the fallback workbook bridging the hours until restore.
